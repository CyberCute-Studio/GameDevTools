# Shared UI and accessibility conventions

## Controls and keyboard behavior

Shared Win32 controls live in `internal/ui`. Use standard `BUTTON`, `EDIT`, `STATIC`, and `LISTBOX` controls rather than custom-painted replacements. Standard controls supply keyboard operation, visible focus, accessibility metadata, and Windows high-contrast behavior. Parent windows must pass unhandled messages through `IsDialogMessageW` so Tab, Shift+Tab, mnemonics, and arrow-key navigation continue to work. Create controls in their layout order, top to bottom: the creation order is the tab order. The keyboard-only audit in [docs/accessibility-verification.md](accessibility-verification.md) records each view's tab order and access keys, and `app.TestTabReachesEveryControlInLayoutOrder` pins them.

A radio group is the run of radio buttons from one created with `Group` to the next control created with `Group`, and its selection is set with `ui.Button.SetChecked` for every button of the group. A radio button is a tab stop exactly while it is checked: Tab enters the group at the selected button and leaves at the next control, and the arrow keys move the selection within it. The dialog manager stops Tab at every tab stop, and a radio button that gains the focus unchecked reports a click, so a group of tab stops would select each button in turn as Tab passed — the navigation's radio buttons switched modules that way — and a group label's mnemonic, which focuses the next tab stop, would select the group's first button.

The main window gives the keyboard focus back when it is activated (`restoreFocus`): Windows focuses a plain window, not the control in it that had the focus, on every activation — at startup, on Alt+Tab, and when the window is shown again after a capture — which would leave no visible focus and restart Tab from the first control. The control that last had the focus gets it back while it is visible and enabled. One disabled meanwhile, as Cancel Resize is when a job finishes while the window is inactive, hands it to the next control in tab order, as a control disabled while it holds the focus does (AC-A03); otherwise, as at startup or with its module hidden, the current module's navigation button gets it. A click that activates the window reaches the control under the pointer after the activation, and that control takes the focus itself, so on a click activation the focus is given back only once the click has been handled, only if the click left it on the window itself, as a click on the title bar or the scroll bar does, and without scrolling the control into view, so the view keeps the scrolling a click on the scroll bar made; giving it back first would run the earlier control's focus handlers for nothing, such as the global shortcut field's suspension of the shortcut. The capture toolbar gives the focus back the same way when it is activated again, by Alt+Tab or the global shortcut, and otherwise keeps it on the toolbar itself. Focus rectangles follow the Windows keyboard-cues setting: unless *Underline access keys* is on, Windows shows them once the user navigates with the keyboard, and the access-key underlines once Alt is pressed.

A dimension input has an adjacent label such as `Width (px)`, a keyboard-focusable edit field, and a validation message directly below it. Field labels immediately precede their edits in tab order and retain mnemonics so Windows can associate the accessible name and keyboard shortcut. Other labels display ampersands literally. Dimension displays use `width × height px` through `ui.FormatDimensions`. Feature modules own their allowed ranges and validation rules; the shared parser only requires a positive whole number representable by `int`.

Chosen paths are displayed in `ui.ReadOnlyText`: a keyboard-focusable, horizontally scrollable read-only edit that keeps long folders readable without allowing manual edits. Folder changes go through `ui.BrowseForFolder`, which wraps the Windows folder picker, returns the absolute path or a cancellation, and requires no manual path entry. `ui.Button.SetChecked` sets radio and check-box state, and feature modules commit edit-field values on the `ui.NotificationEditKillFocus` notification, the same moment shared inputs clear their validation text.

## Validation and errors

Show validation next to the relevant field and explain how to correct it. Errors use `ui.FormatError` so validation, unsupported-format, read/decode, write/encode, clipboard, shortcut-registration, and capture failures remain distinguishable. Error text is always explicit; color is never the only indication of a problem.

## Notifications and confirmation

Use `ui.StatusArea` for non-blocking results. Notices include a textual severity such as `Success`, `Warning`, or `Error`, remain in the window instead of stealing focus, and can expire through a window timer. A status area is a polite UI Automation live region, so a screen reader announces each notice `Show` presents — an identical one included, as an identical result is still a new one — once it finishes what it is reading; `Update` replaces the notice without announcing it, for progress that changes faster than it could be read, such as a resize job's count for every image, whose start and summary are announced through `Show`. Validation messages under fields are live regions too (`ui.NewLiveLabel`), announced when their text changes, and so are the capture toolbar's message and the Image Resizer's detail line for the selected image, which announces as the selection moves and which a resize job's changes update quietly, as the job announces only its start, its Cancel, and its summary. `ui.Label.SetText` announces a live label's changed text; `SetTextQuietly` replaces it without announcing, for a caller that announces the text itself or whose text is not news; and `Announce` reads the current text whether or not it changed, as a refusal repeated on request is news each time: the preset manager's Create and Rename / Save announce a refused field's message again, as each of the capture toolbar's refusals is announced. Text shown in two live regions is announced in one: a global shortcut registration failure, shown beside the field and in the status area, is set quietly beside the field. A hidden window's announcement goes unheard, so two notices shown before they can be heard are announced again once they can be: the shell's startup warning once the window first appears, and a module's notice, such as a global shortcut another application holds at startup, the first time the module is shown in the visible window (`nativeNoticeAnnouncer`), even when another module was current at startup, and from beside the field if a later notice, such as a display failure, replaced it in the status area. A notice set while its module is hidden after that first visit, such as a resize job's summary while another module is shown, is not announced again when the module is shown; it is read when the user reaches it. The shell's own status area is set with `SetText`, so it announces a warning when its text changes, not a repeated identical one; the placeholder note of a module without a native view belongs to its view and is set quietly, so it is not announced on every visit. A label is marked through Dynamic Annotation (`IAccPropServices::SetHwndProp`), which keeps the property in `oleacc.dll`; the package holds that DLL loaded, as COM would otherwise unload it, and the annotation with it, when the apartment initialized for the call ends. A live label destroyed before the process exits clears its marking first (`ui.Label.ClearLive`), as the capture toolbar's message does when its session ends. A zero timeout keeps a notice visible until it is replaced or cleared. Handle timer-creation errors returned by `Show`; the notice remains visible if its timer cannot be created. Replace or clear obsolete results rather than stacking notifications. `Revision` changes whenever `Show`, `Update`, or `Clear` replaces the notice — including by identical text or an expiring timer — so a feature that may later replace only its own notice records the revision after showing it and compares it instead of the text.

Use `ui.Confirm` for destructive confirmation. Its safe answer is the default. Confirmations are modal because they require a decision before an operation; routine status must not use a message box. Result actions such as opening a saved file's folder run only on explicit user request through `ui.RevealInFolder`; the application never opens folders or editors on its own after an operation completes.

## Theme and contrast

Controls use the active Windows system colors. Do not hard-code text, background, border, or focus colors. The shell uses the system window brush, transparent static-text backgrounds, and a DPI-scaled Segoe UI font, while native buttons and edits retain their system rendering. The first release follows Windows' contrast themes this way and does not follow the Windows dark app mode, as standard Win32 controls have no documented dark rendering: the application stays light, legible, and WCAG 2.1 AA compliant when Windows apps are set to dark (UX-008, the PRD's confirmed decision). Custom drawing must verify WCAG 2.1 AA contrast: 4.5:1 for normal text, 3:1 for large text, and 3:1 for essential control boundaries and focus indicators.

The capture overlay's selection ring and resize handles are the application's only custom drawing that must stand out, and they are drawn over whatever is on screen, so no single color can meet 3:1 against every background. They are drawn in two colors — a core edged on each side in the other, as WCAG technique C40 describes — taken from the first pair of system colors that contrast at least 9:1, which guarantees that one of the two contrasts at least 3:1 with any background: the highlight and highlight text, as in the Windows 10 high-contrast themes; otherwise the window text and window background, lighter as the core, which is white edged in black in the default theme and each Windows 11 contrast theme's own text and background; otherwise white edged in black. The measured figures are in [docs/accessibility-verification.md](accessibility-verification.md#contrast).

User-facing text belongs in `internal/ui/strings.go`, the severity and error-category labels included. Feature packages may format dynamic details with those centralized strings rather than defining competing labels. An error's own text — from Windows, the Go libraries, or the application's lower layers, such as the Image Resizer's `decode`, `encode`, `output`, and `job` packages — is the exception: it appears only as the detail after a centralized sentence or label, which the error's kind, not its text, chooses, as the [localization readiness](accessibility-verification.md#localization-readiness) record describes.

## Preset management

The reusable native preset manager in `internal/preset` is embedded independently in Screenshot and Image Resizer. Its combo box selects a preset and restores the persisted selection on startup. Create and Rename / Save validate the name, dimensions, and module-specific fitting mode; Duplicate also works for built-ins; Delete is enabled only for custom presets and requires confirmation. Validation appears below the relevant field, and a refused Create or Rename / Save moves the focus to the field and announces its message, even one already shown, while persistence failures remain visible in the manager's non-blocking status area without discarding in-memory changes.

## Resize job configuration

The Image Resizer view presents the selected preset's fitting mode and its consequence in plain language — including the Stretch distortion warning and the Crop to Fill trimming note — refreshed from the preset library after every preset operation, so the consequence of the job's mode is visible before any job can start. The output format (Keep Source Format, PNG, or JPEG), collision policy (Rename, Skip, or Overwrite), JPEG quality, JPEG transparency background, and output folder persist like the Screenshot capture options. The quality and background fields are disabled only when the format forces PNG output, because Keep Source Format can still encode JPEG sources as JPEG. The collision policy is restated beneath its radio buttons with the exact consequence of the selected policy, including the note that Overwrite replaces existing outputs only after job-time confirmation and never touches source images, saving an output whose existing item is a source image, another output of the same job, a folder or link, or a file that cannot be confirmed not to be a source image under the first unused numbered name so that no other file is replaced, and the note that Skip saves only one of two images that would produce the same file name: the first, or the next if the first cannot be saved.

## Resize source list

The Image Resizer source list is a `ui.ListBox`: a multi-select `LISTBOX` with extended (Shift/Ctrl) selection and change notifications. Each row shows the file name, the upright source dimensions once its content has been checked, and its status (`Checking…`, `Ready`, `Unsupported format`, `Cannot be read`, `Damaged or incomplete`, or `Too large`); selecting an item shows its full path in a `ui.ReadOnlyText` and, on a line below it, either the decoded description — format, dimensions, alpha channel, the applied EXIF orientation with the stored dimensions, and a note when the content does not match the extension — or the reason the item cannot be used. Remove Selected and Clear List stay disabled until they apply. Files are added through the multi-select image picker (`ui.PickImageFiles`, filtered to the supported PNG/JPEG extensions) or by dropping files — or a folder of images — anywhere on the view: the shell registers the window and every child control with `DragAcceptFiles` only while the active module implements `nativeDropTarget`, and a subclass on each child forwards its `WM_DROPFILES` to the shell, which unpacks the drop and delivers the paths to that module, so other modules keep the no-drop cursor. Adding checks each path's extension and existence up front without blocking the valid entries, deduplicates full paths case-insensitively, and never modifies the sources; a dropped folder contributes only the supported files directly inside it, without recursing. Batch results are summarized in the view's status area, including counts of duplicates, unsupported files, and unreadable files. Supported files then stay `Checking…` while their content is decoded one at a time off the GUI thread. Finished checks reach the GUI thread in batches — the view keeps at most one dispatcher post outstanding, so a large drop of small files neither floods the message queue with relayouts nor loses results to a full one, and a refused post is retried until it is accepted, so the last result is never stranded — and each result rewrites only its own row through `ui.ListBox.SetItemText`, which preserves the selection, caret, anchor, and scroll position, so background updates never disturb what the user selected. Because setting a list box's caret raises an accessibility focus event even when the caret stays put, `SetItemText` restores the selection without moving the caret and restores the caret only when the reinsertion moved it: rewriting any other row raises no focus event, so a screen reader does not announce the focused row again for every result, and rewriting the focused row raises one for its new text. When the last check resolves, the status area restates the add results since the list was last fully checked — small files resolve so quickly that the add notice would otherwise vanish — and summarizes how many of the images are ready and how many cannot be resized, counting only the items still listed in both parts, and a skipped duplicate only while the item it matched is; removing the last items still being checked ends checking the same way, with the summary ahead of the removal notice. The summary replaces only the source list's own notice, or an empty status area, so a warning or error raised meanwhile stays visible. Removing or clearing items abandons their pending checks. A check whose read is blocked in the operating system — on an unresponsive network share or an online-only file — cannot observe that, so removing its source also sets its worker aside and lets the remaining checks continue at once, however many removed sources are still blocked; a set-aside worker exits as soon as its read returns, or once a decode whose reads were done finishes, and until then keeps what its check had allocated while the next check runs. Closing the window cancels the in-flight check without waiting for it, so a blocked read never holds the process open.

## Resize jobs

Start Resize is the shell's primary action for the Image Resizer. A module view whose primary action is unavailable for a while implements `NativeActionAvailable`; the shell disables the action button while it reports false and re-reads it on every relayout, which follows every module command, action, and dispatched task. Before it disables the button while the button has the keyboard focus, the shell moves the focus to the next control in tab order, so the focus is never stranded on a disabled control; a view may move it first to a better place, as Start Resize moves it to Cancel Resize. A drop target that refuses drops for a while implements `NativeDropAvailable`; the shell registers the window for drops only while it reports true, re-read on every relayout, so a drop the view would refuse keeps the no-drop cursor.

Before a job starts, the view checks that no image is still being checked, at least one is Ready or is to be checked again, the selected preset is valid, and the JPEG quality and background fields and the output options are valid; the fields are applied from their text, as Start Capture applies the Screenshot quality field, because starting from the keyboard need not move the focus. A refusal is shown in the job section above the source list — a field the options refuse to apply, as while no output folder is selected, included — and an invalid field's message also beside the field. The job first checks again, on its own goroutine, every image whose content check failed or that could not be found when it was added, unless its extension was refused, so a re-run takes each image as it now is (RSZ-049); until the job reports, the job section says so, as no image starts until those checks finish, which a source on a drive that is not responding delays. A job cancelled meanwhile ends the images it had not checked again Cancelled rather than Failed with their earlier reasons, and the list shows the checks made from the job's first event on, so a row checked again shows its dimensions beside its job state, or once the job ends, however it ends, a job the view let go included. Under Overwrite, `ui.Confirm` asks before the job starts, with No as the default; declining starts nothing, and, as its modal loop still dispatches messages, a forwarded drop among them, the list is checked again once it is answered. A refusal or failure uses `ui.FormatError` so validation, unsupported-format, read/decode, write/encode, and unexpected failures stay distinguishable (`ui.ErrorUnexpected` labels a failure no step classified, such as a contained panic).

The job runs off the GUI thread. Its events reach the GUI thread through the shell dispatcher in batches — at most one post outstanding, keeping only each image's latest event, and retried when refused — so the window stays responsive whatever the batch size (AC-A04). While it runs, the source list cannot change, as its rows are the job's items: Add Images, Remove Selected, and Clear List are disabled, drops keep the no-drop cursor, and a command or drop that arrives all the same — an add the Add Images picker returns once a job started while it was open included — is refused, as is a Start Resize, with a notice in the view's status area, which leaves the job section to the job's progress and which the job's end clears while the status area still shows it; selecting an image still shows its state. Each row shows its image's state in words (Pending, Processing…, Completed, Skipped, Failed, Cancelled), rewritten in place through `ui.ListBox.SetItemText` only when its text changed, so the focused row is not announced again for nothing, and the selected image's detail line says where its result was saved and why under a numbered name, which file a skip left untouched and why, why it failed with the error's category and how to recover where that applies, or that it was cancelled, and names any file a write could not remove. The job section's `ui.StatusArea` shows the done and total counts by outcome and the file that most recently started processing, keeping the height of the longest progress the job can show — every count at the total and its longest file name, measured once for each width and scale and kept for each on its own — and never shrinking while the job runs, so the source list below it does not move between files; a name that renders wider than the longest by bytes, such as one of wide letters, can grow the section once. Then it shows the summary of Completed, Skipped, Failed, and Cancelled images: a success, a warning when any failed or was cancelled or left a file behind — a temporary file, or a replaced file that could not then be deleted — or an error when every image failed; it reads as cancelled only when an image was. A job that stops unexpectedly after it started — a panic its goroutine contained — keeps what it reported, and its images that had not ended are Failed with the unexpected error. Cancel Resize is enabled only while a job runs; choosing it moves the focus to the source list and disables it. A cancelled job that has not stopped within five seconds, because a read or write blocked in the operating system cannot observe the cancellation, is let go: its events and outcome no longer reach the view, which shows its images still in flight Cancelled with an explanation — that a read or write may not be responding, as the view cannot tell a blocked call from a step slow to reach its next safe point — and the others as they ended, or as a cancelled job ends them: Failed with why when the job could not use them, and Cancelled otherwise, so Start Resize and the source list are available again. Open Output Folder is offered once the job's folder holds a result — a job that saves none leaves the previous job's folder offered — and opens it through `ui.OpenFolder` only when chosen, on a goroutine of its own, as looking at the folder and the shell's call each block for as long as its drive does not respond, and a failure is shown through the dispatcher in the view's status area, as the Screenshot view shows its own Open Folder failure, so it neither replaces a finished job's summary nor is hidden by a running job's progress; `ui.OpenFolder` refuses a path that is not a folder and uses the shell's folder-only explore verb, so it never opens or runs a file in a folder's place, keeps its goroutine on one thread while it holds the COM apartment it initializes, and returns only once the shell has finished opening the folder (`ShellExecuteExW` with `SEE_MASK_NOASYNC`), as the goroutine's thread runs no message loop through which the shell could finish it later. Settings changed while a job runs apply to the next job. Closing the window cancels a running job, and shutdown waits up to ten seconds for every job's images in flight to stop; a second launch meanwhile waits for the closing instance to exit and then starts.

## Capture overlay sessions

Rectangle capture opens a selection session: the main window hides first, then the mode's session surface appears and a floating topmost toolbar offers Capture and Cancel. Every session surface is visible while it intercepts input, and its `WS_EX_NOACTIVATE` style keeps it below the toolbar and unfocused; the toolbar is activated to take keyboard focus instead. Escape, Cancel, and closing the toolbar (for example with Alt+F4) are equivalent and end the session without output. The toolbar uses standard controls and system colors; the shell's message loop forwards its messages through `IsDialogMessageW` via the module's `NativeFilterMessage` hook so Tab, arrow keys, and Enter keep working while the shell window is hidden, with Enter inside a dimension field committing the value instead of activating Capture. Session windows are unowned popups, so every exit path — cancel, capture, session failure, or application shutdown — destroys them explicitly and restores the main window. If the display topology changes mid-session, the session is revalidated against the new virtual desktop: a selection that still fits keeps its exact dimensions and is moved back inside, the tint overlay or preset frame and the toolbar are resized and repositioned, and a selection that can no longer fit ends the session with an explanatory warning rather than leaving a stale overlay up (SCR-054, AC-S12).

In a Free Rectangle session, a per-pixel-alpha topmost overlay dims the virtual desktop, and dragging on the dimmed surface draws the selection, whose interior stays visually clear — painted at the minimum imperceptible alpha, because a layered window's alpha-zero pixels would let mouse input fall through to the windows beneath — while the rest of the desktop remains dimmed; the live width and height appear in the toolbar's dimension fields. After the drag, dragging the interior moves the rectangle, the eight handles resize it, and typing exact width and height values resizes it in place, with invalid or non-fitting values rejected and reverted. The session can also be completed without a pointer (SCR-015): it starts in the toolbar's width field, and with nothing drawn, typing a width and height and pressing Enter creates a selection of exactly that size, centered on the cursor display's work area and kept inside the virtual desktop — moving from one field to the other is not a request, so a corrected pair is still centered, and neither is leaving the fields with one still empty, nor switching to another application, after which the field gets the focus back, while leaving them filled for another toolbar control commits the size as Enter does, and Enter with a field empty, or a size larger than the desktop, explains the problem and keeps the typed text — the Enter that creates the selection hands the focus to the Capture button the selection enables, where Enter captures, and Tab out of the filled pair creates the selection before the focus moves, so it lands on Capture too rather than passing it, still disabled, for Cancel; once a selection exists the arrow keys nudge it by one physical pixel, or ten with Shift, except inside the dimension fields. Drawing with the pointer hands the focus from a dimension field to the toolbar, so Enter then presses Capture, and ending the session commits nothing still typed in the fields. A display change leaves a size typed with nothing drawn in the fields. The toolbar's message is a live region that announces the instructions when the session starts and each refused size; a message that returns to the instructions while the user types is not announced again. The toolbar follows the selection, sitting below or above it without covering the content where practical, and stays clamped inside the virtual desktop. Capture stays disabled until a selection exists. The Capture command destroys the session windows, reads the rectangle's pixels off the GUI thread while the main window is still hidden, and only then restores the window, so the tint, frame, handles, toolbar, and cursor can never appear in the output.

In a Preset Rectangle session, the selected preset floats above the desktop as an exact-size topmost frame centered on the cursor display; the desktop keeps its normal appearance. The frame's alpha-zero interior is visually unobscured and click-through, so the underlying application receives clicks inside the frame while the frame retains its position and dimensions — losing activation never cancels the session. The opaque border ring is the only part that captures input, and dragging it moves the frame, including across display boundaries, without changing its dimensions; there are no resize handles, so the exact size changes only through typed dimensions or preset selection. The toolbar shows the live width and height in editable fields plus a virtual-desktop X/Y readout, and its Capture command starts enabled. While the toolbar has keyboard focus, arrow keys nudge the frame by one physical pixel, or ten with Shift, except inside the dimension fields where they keep editing the text; after a click-through into another application the keys belong to that application until the toolbar is focused again (SCR-027). Typed dimensions resize the active frame exactly in place as an ad hoc edit that never modifies the saved preset, with invalid or non-fitting values rejected and reverted. A preset larger than the entire virtual desktop is rejected with a validation message before anything hides, while a rectangle larger than one display is allowed whenever it fits the virtual desktop. Capture and cleanup behave as in Free Rectangle: the frame's border ring is painted outside the captured rectangle, and the session windows are destroyed before the pixels are read, so the frame and toolbar never appear in the output.
