# Settings, recovery, and shutdown verification

This document is the QLT-02 record for settings migration and recovery, restoring the default settings, and application shutdown: APP-004, SET-004, SET-005, SET-006, NFR-020 through NFR-024, and the shared acceptance scenarios AC-A01 (persistence) and AC-A05 (clean exit) from [PRD section 15.3](../PRD.md#153-shared-acceptance). It records how the checks run, the settings files the upgrade test loads and where they came from, the recovery, restore, and exit matrices, what was found and fixed, the result for each requirement, and what remains to check by hand.

## How to run the checks

From the repository root on Windows:

```bash
go fmt ./...
go vet ./...
go test -count=1 ./...
```

`go test` runs every check below. To run only this record's own tests:

```bash
go test -count=1 -v -run 'TestOpenSession|TestRestoreDefaults|TestStartupWarnings|TestClose|TestEndSession|TestSavedPlacement|TestWorkspaceOffset|TestWaitForBackgroundWork|TestFailedSave|TestExitDuring|TestStartingWork' ./internal/app
go test -count=1 -v -run 'TestStoreRestore|TestStoreBackup|TestStoreLoadRemoves|TestStoreHold|TestNativeView' ./internal/settings
go test -count=1 -v -run 'TestOptionsManagerReload|TestNativeViewRestoreDefaults' ./internal/screenshot
go test -count=1 -v -run 'TestOptionsManagerReload|TestFolderWarning|TestNativeViewRestoreDefaults|TestNativeViewAsksBeforeClosing' ./internal/imageresizer
go test -count=1 -v -run 'TestLibrarySection|TestKeptSection|TestManagerReload|TestNativeManagerReload' ./internal/preset
go test -count=1 -v -run 'TestConfirmAnswersNo|TestStatusAreaClearShown' ./internal/ui
```

The tests in `internal/app` build the real main window with every production module on a temporary settings file, through the same `openSession` and `newNavigator` the application starts with, and open real capture sessions and run real resize jobs, so run them in an interactive desktop session, as the module suites are run. They register the Screenshot global shortcut as Ctrl+Alt+Shift+F24 rather than the default Ctrl+Alt+S, as the accessibility audit's tests do, and the shell-level restore tests stand in for the Screenshot view's restore, which would register Ctrl+Alt+S machine-wide; `internal/screenshot`'s restore tests cover that view with a fake registrar. Windows CI (`.github/workflows/ci.yml`) runs the same commands on every pull request.

## Upgrade results

`TestOpenSessionUpgradesEverySettingsFormat` loads each file with every section owner's validator registered, as the application starts. Every file passes:

- Nothing is reported, rewritten, or backed up, but for the legacy folder, which loads as the default folder with one warning naming the stored folder.
- The window placement, the selected module, both modules' custom presets and selected presets, and every stored option load as the build stored them; what the build did not store loads as its default.
- After a normal restart — the session saved as the window closes, and the file loaded again — every value is the same (AC-A01). The legacy folder's warning repeats until the resize options are next saved, as [docs/settings.md](settings.md#image-resizer-resize-options) documents, and is gone after that save.

## Recovery matrix

`TestOpenSessionRecoversFromMalformedSettings` corrupts the newest file in fifteen ways and loads each through the application's wiring: a truncated file, trailing data, a future version, a window too small, an unknown module, a module section that is not an object, an unknown capture mode, a shortcut without a modifier, an unknown capture field, a custom preset named as a built-in, an unknown selected preset, a resize preset without a fitting mode, an unknown collision policy, a malformed background, and a relative output folder. Every case passes (SET-006, PRESET-008):

- The file is copied byte for byte to `settings.json.corrupt-<timestamp>`, the copy read back and compared before defaults replace the original, and one warning names the copy.
- Both modules keep their built-in presets, and the options load as their defaults.
- A restart loads the regenerated file without a warning.
- A source image beside the settings and saved images in both default output folders are not touched.

The store's own tests cover the paths that keep the original instead: an unreadable file, and a backup that cannot be created or that fails verification (`TestStoreBackupThatFailsVerificationBlocksSaving`), each disable saving for the session. `TestStoreLoadRemovesStaleTemporaryFiles` covers the cleanup of temporary files an interrupted save left.

## Findings and fixes

| Finding | Fix |
|---|---|
| There was no way to restore the default settings (SET-005): the Settings view was a placeholder. | The Settings view's Restore Default Settings, as [docs/settings.md](settings.md#restoring-default-settings) describes, which keeps both preset libraries and their selections, the window, and the current module, as decided for QLT-02. |
| Signing out of, restarting, or shutting down Windows was not handled. Windows may terminate the process once `WM_ENDSESSION` returns, before the message loop's end, so the window placement since the last navigation was not saved, a running resize job was not cancelled, and its images in flight could leave their temporary files in the output folder. | The shell shuts down inside `WM_ENDSESSION`: it destroys the window — releasing the shortcut, closing overlays, cancelling the job — before writing anything, then saves and waits for the work, asking nothing, for at most three seconds, so a save or work that does not stop, which a capture's wait would otherwise wait for without limit, never holds the session's end up. |
| Closing the window while a resize job ran cancelled it without asking. | The close asks first, No the default, unless the user already cancelled the job. |
| A window minimized from maximized was saved as not maximized, which the save at the end of the Windows session would do at every sign-out while it was minimized, and its bounds were saved in workspace coordinates, which a taskbar at the top or left of the screen offsets from the screen coordinates the window is created at. | The placement saves a minimized window as it is restored, and its bounds in screen coordinates. |
| A backup was trusted once it was written. | Every backup is read back and compared before the original is replaced; one that differs is removed and treated as a failed backup, which keeps the original and disables saving. |
| A save interrupted before its rename left its temporary file in the settings directory for good. | Loading removes such files once they are more than a day old, as a redirected settings folder's server clock can be minutes off. |
| A session whose saving recovery had disabled could only be left by fixing the file by hand. | Restore Default Settings backs the file up, and saving works again once it has. When the session started from the defaults because the file could not be read, the restore keeps the presets the file stores, with the ones the session created, and the modules show them, and the shell's note drops the startup warnings about the file. |
| The upgrade and recovery behavior was tested only on the settings store, with invented data and without the section validators the application registers. | The fixtures above, loaded through the application's own wiring (`openSession`, extracted from `runNative`). |

## What these results do not cover

- **A real sign-out.** The end of the Windows session was exercised by sending `WM_QUERYENDSESSION` and `WM_ENDSESSION` to the real main window, as Windows does, rather than by signing out, which would end the test's own session. Before release, sign out with a resize job running and confirm, after signing back in, that the output folder holds no temporary file and that the window opens where it was.
- **Windows' shutdown time limit.** Windows may terminate an application that has not returned from `WM_ENDSESSION` within a few seconds, and shows a list of applications holding up the shutdown. The shell waits for the settings save and the work in flight for at most three seconds from the message's arrival, which was not measured against a real sign-out. The save, a job's images in flight, and a capture's delivery normally finish at once; one blocked on an unresponsive network drive is then ended with the process. A job's `.gamedevtools-*.tmp` file may then remain in the output folder; it holds at most that one unfinished result, which was never saved under its own name, so it is safe to delete. A settings save so ended leaves the settings file as it was, and its `.settings-*.tmp` file is removed by a launch once it is a day old, as [docs/settings.md](settings.md#recovery-and-writes) describes. A save blocked in that way was not reproduced, as no test here makes a write block. Nor was a field committing its edit as the window is destroyed: only the foreground window's destruction takes the focus from a field while the shell still routes its commands, and a test's window is not the foreground one, so a module view that saves as it is destroyed stands in for it.
- **Released versions.** No version has been released, so the fixtures are what each merged build wrote. A release should add the file its build writes as a fixture.
- **A full disk.** Write failures were made by a read-only file and by a folder in the file's place, not by a disk that runs out of space during the write or the backup.
