# CyberCute Dev Tools

CyberCute Dev Tools is a Windows desktop application implemented in Go. The repository contains the production project foundation under `cmd/gamedevtools` and `internal`, plus the separate **FND-01 technical spike** under `cmd/fnd01-spike`.

The production application provides a native Win32 main window with Screenshot, Image Resizer, and Settings navigation. Both feature modules include independent preset management. The Screenshot module configures its capture mode, output format, JPEG quality, and output folder, and captures a selected display, a user-drawn rectangle, or an exact preset-sized rectangle end to end. The Image Resizer module builds a deduplicated, per-file validated source list from a multi-select image picker or drag-and-drop, manages resize presets with their fitting modes, and configures the resize job's output folder, format, collision policy, JPEG quality, and JPEG transparency background; Start Resize then resizes every ready image in the background, with live progress, Cancel Resize, each image's result in its row, a completion summary, and an Open Output Folder action. The spike validates native Windows integration for the Screenshot module. See [ADR-0001](docs/adr/0001-native-windows-stack.md) for the stack decision, license inventory, verification results, and open mixed-DPI validation blocker.

## Production application

The module targets Go 1.25 and names the Go 1.27.4 toolchain in `go.mod`. The `go` command downloads and uses that toolchain automatically, unless a newer Go is already installed, which it uses instead, or `GOTOOLCHAIN=local` is set. Set `GOTOOLCHAIN=go1.27.4` to build with exactly the release toolchain; CI fails a release executable built with any other. No C compiler or CGO is needed. Built executables run without a Go installation or development toolchain.

Start the application shell with:

```bash
go run ./cmd/gamedevtools
```

Use the navigation controls — clicked, or with the arrow keys once Tab has reached them — to switch between Screenshot, Image Resizer, and Settings. Each module retains its view object while another module is selected. In either feature module, use the preset fields to create a custom preset, Rename / Save to update the selected custom preset, Duplicate to copy any preset, and Delete to remove a custom preset after confirmation. Shared registration, navigation, and GUI-dispatch contracts live in `internal/shell`.

The Screenshot module also configures the capture mode (Free Rectangle, Preset Rectangle, or Full Display), the PNG/JPEG save format, JPEG quality from 1–100, the global capture shortcut, and the output folder, which defaults to `Pictures\CyberCute Dev Tools\Screenshots` and is chosen through the Windows folder picker. All options persist across restarts. In Full Display mode a picker lists every connected display with its number, name where Windows provides one, native resolution, scaling, and primary status, defaulting to the display under the cursor and refreshing when the display topology changes. Start Capture hides the main window, captures the selected display at its native pixel dimensions, copies the original pixels to the clipboard, saves the timestamped file, restores the window without stealing focus, and reports the clipboard and save outcomes independently in a non-blocking notification with an Open Folder action. In Free Rectangle or Preset Rectangle mode Start Capture opens the selection session described below, where the drawn rectangle or the exact preset frame is captured and delivered the same way.

The global shortcut, `Ctrl+Alt+S` by default, starts the currently selected capture mode while another application has the foreground. It is registered on the main window, so it works even while that window is hidden behind a selection session; invoking it during a session brings the existing selection's toolbar back to the foreground instead of stacking a second overlay. A combination another application already owns is reported as a shortcut-registration conflict beside the field and in the status area, the previous combination keeps working, and a replacement typed into the shortcut field is validated, applied, and persisted without reinstalling. The shortcut is suspended while its field is being edited or one of the application's modal dialogs is open, and released when the application exits. A capture the shortcut starts while the Screenshot view is not in front reports its outcome on a small always-on-top card in the corner of the display under the pointer, which never takes the focus: a success leaves by itself, a warning or error stays until it is dismissed, on the card or with the Screenshot view's Dismiss Problem button, and the card is hidden during every capture so it cannot appear in an image.

The Image Resizer module accepts PNG and JPEG sources through a multi-select file picker and through files — or a folder of images — dropped anywhere on its view. Each added file's content is decoded in the background to validate it rather than trusting its extension, and the source list shows each file's name, upright dimensions once checked, and status, with the full path and a description — format, alpha channel, applied EXIF orientation, or the reason a file cannot be used — shown for the selected item; duplicates are skipped, and sources are opened read-only and never modified. Items can be removed or the whole list cleared before a job starts. The module persists its job configuration across restarts: the output folder, defaulting to `Pictures\CyberCute Dev Tools\Resized` and chosen through the Windows folder picker; the output format — Keep Source Format, PNG, or JPEG; the collision policy — Rename, Skip, or Overwrite — with the selected policy's consequence restated beneath it; JPEG quality from 1–100; and the `#RRGGBB` background color transparent pixels are flattened against when JPEG output is produced. The selected preset's fitting mode is explained in plain language alongside, including the Stretch distortion warning. Start Resize runs the job described below for every listed image.

The selected module and normal window bounds persist across restarts. Only one instance runs per user session: a second launch activates the existing window — restoring it first when minimized — and exits, so global shortcuts and settings never conflict across instances; one that lands while the running instance is closing, its window gone while a resize job's images in flight stop, waits for it to exit and then starts. Closing the window while a resize job runs asks first, as closing cancels the job; when Windows signs out, restarts, or shuts down, the application asks nothing, saves its settings, releases the global shortcut, closes any capture overlay, and cancels a running job before the session ends. Settings use a versioned JSON file with atomic writes, migration hooks, and backup-before-recovery behavior. The Settings view's Restore Default Settings backs the settings file up and returns the global shortcut, capture and resize options, and output folders to their defaults, keeping custom presets, each module's selected preset, the window, and every image. Diagnostic logs contain structured event metadata only and rotate by size. See [Local settings and diagnostics](docs/settings.md) for paths, schema, recovery, and redaction boundaries.

Independent Screenshot and Image Resizer preset libraries live in `internal/preset`. Built-in dimensions are immutable; custom presets have stable local identifiers, validated module-specific options, and persistent storage within their owning module's settings section. Malformed preset data uses the same backup-and-recovery flow as the rest of the settings file.

Source decoding lives in `internal/imageresizer/decode`. The package identifies PNG and JPEG content by its file signature, so a renamed file is decoded as what it actually contains; decodes it with the Go standard library decoders, which cover baseline and progressive JPEG (including CMYK and grayscale) and every standard PNG color type and bit depth; and applies the JPEG EXIF orientation — all eight standard values — so reported dimensions and pixels are upright. Failures are typed, so unreadable files, unrecognized content or unsupported coding features such as arithmetic-coded or 12-bit JPEG, damaged or truncated data, and oversized sources are reported distinctly. A source whose decoding would need more than 1 GiB of pixel memory — the decoded image at the decoder's pixel size for its color type, plus the decoder's working buffers, such as an interlaced PNG's pass images, a PNG's row buffers beyond a small allowance, a progressive JPEG's coefficients, or a JPEG's RGB conversion, and the upright copy of a reoriented JPEG — is rejected before anything is allocated. `Info.DecodedBytes` reports the pixel memory a source's decoding needs, and `DecodeWithin` decodes a source only within such an allowance, failing one that needs more, as a source rewritten since its check may, with `ErrOverAllowance` before anything is allocated. Metadata other than the normalized orientation is neither read nor preserved. The Image Resizer view runs these content checks one file at a time on a background goroutine, returning a large check's pixel memory before the next one starts, and hands the results to the GUI thread in batches through the shell dispatcher; a check abandoned because its source was removed is not waited for, so until it stops its memory adds to the next check's.

Resize geometry and resampling live in `internal/imageresizer/resize`. `Plan` computes the output dimensions from the upright source dimensions and the preset: Stretch produces exactly the preset dimensions; Fit scales uniformly by the smaller of the width and height ratios, rounds the other dimension to the nearest pixel (halves up), and clamps it to at least one pixel, so a 1000 × 500 source fits a 512 × 512 preset as 512 × 256; and Crop to Fill scales uniformly by the larger ratio, rounding the same way, then crops the overflowing axis equally from both sides, taking an odd leftover pixel from the right or bottom, so the same source scales to 1024 × 512 and keeps the centered 512 × 512. Every mode enlarges as readily as it reduces. Targets are validated with the preset library's own rules — 1 to 16,384 pixels per axis and at most 100 megapixels — and sources wider or taller than 1,048,576 pixels are rejected as too large, which keeps the filter's working memory bounded whatever the source's shape. `Resize` resamples with a separable Catmull-Rom cubic filter, widened when reducing so every source pixel contributes, filtering premultiplied alpha so transparent pixels lend no color to their neighbors, storing a pixel whose alpha rounds to zero as transparent black, and clamping the filter's overshoot; the stored sRGB values are filtered directly rather than in linear light, and JPEG YCbCr and CMYK pixels are converted to RGB exactly as the decoder converts a reoriented JPEG, so reorienting a picture does not change the colors the filter starts from. Crop to Fill resamples only the region it keeps. The output keeps the source's kind of pixels — grayscale, opaque color, or translucent color, at 8 or 16 bits per channel, judged by the pixels the filter reads, so translucency only in a margin Crop to Fill removes adds no alpha channel — and resizing to the source's own size changes no straight-alpha 8-bit, grayscale, or opaque pixel, except that a fully transparent pixel comes back as transparent black whatever color it stored. Results are bit-identical for the same source and preset on every 64-bit platform, the only kind the package builds for: sample positions are exact ratios, filter weights are quantized to fixed point from float64 arithmetic that cannot fuse into platform-dependent multiply-adds, each within one unit of its exact value, and pixels are filtered in integer arithmetic. The filter streams the source a row at a time, resampling rows or columns first according to a cost estimate that weighs how costly each kind of source pixel is to read, within a fixed budget for the rows it keeps, so beyond the output image it needs a few megabytes for typical sources and under 128 MiB in the worst case, weight tables included, which `WorkingBytes` bounds for a source's dimensions, and a context cancels it between source rows and before it allocates the output. A panic during a resize, such as one a malformed source image's own methods raise, is returned as that resize's error rather than crashing the caller. Encoding and saving the result, and running batches, are described below.

Output planning lives in `internal/imageresizer/output`, which imports no other Image Resizer package but `decode`, so the view and the job that runs it can both use it; it defines the output format and collision policy values and the output folder rules the persisted options use. `Prepare` validates a job's output folder, format, policy, and sources, refusing a folder path that Windows would resolve to another path, judged by comparing the path, both as written and as `filepath.Clean` writes it, which is the form planned into, with Windows' own resolution of it rather than by a model of its rules — such as one whose own name ends in a space or a period, which Windows drops from the last name of a path, one through a name that ends in a single period, which Windows drops from a name a path leads through, or one that ends in a device name such as `NUL` — unless the path is an extended-length path marked `\\?\` with backslashes, which Windows takes verbatim, while it resolves the same prefix written `//?/` like any other device path; a path with a colon after its drive or share, in any spelling, which NTFS reads as a file stream, so `Resized::$INDEX_ALLOCATION` would name the folder `Resized` under another spelling, or in a share's server or share name, which neither may hold; a path that names only a drive, volume, device, or server, such as `\\?\C:` without its root separator; a device path that leads to no drive, volume, or share, such as the named pipe `\\.\pipe\x`, or a server's `pipe`, `mailslot`, or `IPC$` share, such as `\\localhost\pipe\x`, which creating the folder would open; and a network path whose server or share is not a plain name, such as `\\server\..\x` or a path with three leading separators, since its text does not say what Windows would connect to, as well as a source path Windows resolves to a device, such as `C:\In\NUL`, which leaves no name for its result; it creates the output folder when it does not exist, through its extended-length path, so a name Windows keeps in a path that leads through it, such as `Photos ` or `v2..`, is created as named rather than shortened, and gives every source one destination in that folder before anything is written: the source's base file name with the extension of the encoded format, `.png` or `.jpg`, where Keep Source Format encodes each source as its detected content format, so a JPEG saved with a `.png` extension produces a `.jpg` output. Collisions follow the job's policy. Rename appends `_2`, `_3`, and so on until a name is neither an existing file, a source, nor another item's destination; Skip leaves the existing destination untouched and marks the item skipped; Overwrite replaces an existing destination file only when the request carries the user's explicit confirmation for the job, and is refused without it. Two sources that would produce the same destination never share it: the first in the job keeps the name, and a later one is renamed, or under Skip deferred (`ActionDefer`), while a source whose own name is free always keeps it rather than losing it to another item's numbered name. A deferred duplicate records the item it defers to, and `Plan.Successor` names the duplicate that creates the name when that item fails without writing it, so a Skip job still saves one result per name, while a file another program writes at the name after planning is an existing destination that ends them all Skipped. Overwrite replaces only a result's natural destination: a result it renames takes the first unused numbered name, as under Rename, because a file with a numbered name, such as a `photo_2.png` beside the `photo.png` being resized into its own folder, may be an original nobody listed rather than an earlier result, so re-running an Overwrite job adds a new numbered copy of each renamed result. No plan ever writes over a listed original: destinations are compared by path, as Windows resolves it and case-insensitively, with every source and with every other listed path the job does not process, such as a file too large or corrupt, or a dropped folder or drive root the list could not read, which does not fail the job, and before Overwrite replaces an existing file it also compares the file's Windows file identity with theirs, so a hard link, a junction, a short name, or another alias of a listed file is recognized as that file; the file index alone decides, without the volume serial number, because a Samba server reports a serial number of its own for each share, so one file reached through two of its shares would otherwise look like two. A destination that is a source is renamed under Rename and Overwrite and skipped under Skip, and Overwrite replaces only a file it can prove is none of them, renaming the result when the file's identity cannot be read or when it may be a listed file whose identity cannot be read: a plain file the user may not open, in a folder that can be read, can only be an existing file in that same folder or one with more than one name, while a listed file that cannot be located at all, because its folder, drive, or share cannot be reached, may be any file, and only a file missing from a folder that exists counts as gone, even where a network redirector reports a missing folder as a missing name, and never a listed link whose target cannot be found, a listed path through a device other than a drive, volume, or share, such as a named pipe, is never opened and, since it may still lead to a file, stops a confirmed Overwrite from replacing anything, while a listed folder that can still be inspected is no file, whether or not it can be read, and neither is a drive or share root, however it is reached, but a listed folder that cannot be inspected at all, as when its drive or share has gone, cannot be told from a file that cannot be located, since a listed path does not say it named a folder; Rename and Skip never replace anything and read no identities. A file whose reparse point only says how its data is stored, such as one OneDrive keeps in sync, is a file like any other, while a folder, a link, or a junction at a destination is never replaced, and neither is a file the output's name reaches only as its 8.3 short name, such as a `photograph.png` that `PHOTOG~1.png` opens; an existing entry its folder cannot list is renamed past as unverified. A destination name Windows would open as something other than a file in the output folder, as Windows 10 opens `NUL.png` as the `NUL` device, counts as taken, as an existing entry's name does, though with its own reason, `ReasonDevice`, since nothing exists there, and the device is never opened. Each run inspects the folder as it stands, so re-running a job plans around its earlier results, and because a source could still be moved or linked to a replaced file's name after planning, `Item.StillReplaceable` tells the writer whether the entry is still a file its folder lists under the destination's own name, not a link put there since, which would reach the planned file wherever it now has its name, and still the one the plan proved is no source, unchanged: the same identity, number of names, size, and creation and last-write times, since a name the file gains may be a listed path, and a FAT32 or exFAT volume can give a file that takes another's folder entry that file's identity. A request, confirmation, or folder failure fails the job with a typed error — a permission, invalid-path, or missing-drive failure creating the folder is reported as a folder failure, and only a file, or a link that leads to no folder, such as a junction whose target was deleted, standing where the folder or one of its parents should be as `ErrNotFolder` — and so does an output folder that can no longer be reached, or is no longer a folder, while the plan is made, found when a destination cannot be checked, while a destination that cannot be checked in a folder that is still there, a name longer than 255 characters, a source name with a colon wherever it falls, as a path to a file's stream has, whose output would be a stream of another file in the output folder or named after the file that holds the stream, or a Rename search that finds no unused name within 9,998 numbers fails only its own item; the search passes over a numbered name it cannot check. `CheckFolder` makes the same check of a plan's folder later, creating nothing. `Write` saves each result, and `job.Run` runs a whole job, as described below.

Result encoding lives in `internal/imageresizer/encode`. PNG output is lossless and keeps the resized result's kind of pixels — grayscale, opaque color, or color with alpha, at 8 or 16 bits per channel — so transparency survives, and an alpha channel is written whenever a pixel is translucent. JPEG output has no alpha channel, so a translucent pixel is flattened against the job's background color, white by default, in proportion to its alpha: a fully transparent pixel takes the background color and an opaque one keeps its own. JPEG output rounds 16-bit samples to the nearest 8-bit value and uses the job's quality from 1 to 100. A grayscale result, which has no alpha, stays a one-component grayscale JPEG; a result with alpha is flattened in color, since the background may be any color, so a gray picture with transparency, which is decoded and resized as color with alpha, gives a color JPEG. The blending and rounding are integer arithmetic, so the same result and options give the same bytes on every platform. No metadata is written — no EXIF, so no orientation tag, as the pixels are already upright, and no ICC profile, comments, or timestamps. To keep memory bounded, JPEG output converts the result's pixels in place rather than in a copy, changing no byte outside the result's own pixels. A panic while encoding is returned as that result's failure rather than crashing the caller.

`output.Write` saves one planned result. The encoder writes into a new temporary file named `.gamedevtools-*.tmp` in the output folder, which is flushed to the drive and renamed to the destination only once the result is complete, so no partial file ever has a destination's name; a failed or cancelled write removes its temporary file and leaves the destination as it was, and a temporary file it cannot remove is reported with `ErrLeftBehind` beside the failure that ended the write. A result created under a name that was free when the job was planned is renamed there without replacing anything, so a file another program wrote at that name since is never overwritten and the item fails with `ErrDestinationTaken`, before the result is encoded when `Item.CheckWrite` already finds the name taken. A confirmed Overwrite item replaces only the file the plan proved is none of the sources, unchanged: `Item.CheckWrite` looks at that file before the result is encoded, so one that changed since planning or is read-only fails the item before its work is done, and Write then opens the file so that no other program can write to, move, rename, replace, or delete it while it is held, makes `Item.StillReplaceable`'s own check with the identity read through that handle, so the file is still the planned one with the same identity, number of names, size, and creation and last-write times, moves it aside by the same handle under a name that starts with `.gamedevtools-replaced-` and ends in the destination's extension, renames the result into its place without replacing anything, and then deletes the file it moved aside, again by that handle, with POSIX semantics where the file system has them, as NTFS does, so its name is gone at once even while a viewer, the search indexer, or a virus scanner still has the file open — so the only file a replacement ever removes is the one it checked, with the content it checked, whatever another program does at the destination meanwhile. For that instant the destination's name is free, never partial; when the result cannot take it, the moved file gets its name back, and when another program took the name meanwhile, the item fails with `ErrDestinationChanged` and the moved file keeps the `.gamedevtools-replaced-` name the error gives. A source moved or linked to the destination since planning, a rewritten file, or a folder or link put there is never replaced (`ErrDestinationChanged`); nor is a read-only file (`ErrReadOnly`); a file another program holds open for writing, or without allowing deletion, fails the item with the sharing violation once Write has waited a fraction of a second for it to be closed, so a brief read by a thumbnail generator or a sync client does not; and a planned file deleted since is not needed, so the result is created in its place. Holding the file does not stop another program from changing its attributes, so a file marked read-only after Write checked it cannot be deleted once the result has its name: it keeps its `.gamedevtools-replaced-` name, which the error names. Failures are typed per item: a permission failure is reported as `fs.ErrPermission`, a full drive or a used-up storage quota as `ErrDiskFull`, an output folder removed since planning as not existing, and an existing file that cannot be inspected as the write failure it is rather than as a change; an item that saves no file, or has no absolute destination, is refused by `Item.CheckWrite` before any work is done for it, as is an item whose name another program took since planning and a confirmed Overwrite item whose file changed or is read-only. A process killed mid-write can leave a `.gamedevtools-*.tmp` file in the output folder, which holds at most a result and is safe to delete, but never a partial file at a destination; one killed between a replacement's two renames leaves the file being replaced as a `.gamedevtools-replaced-*.png` or `.jpg` file, the original picture, which can be renamed back.

`job.Process` takes one planned item end to end: it checks the item, including whether its name was taken since planning and a confirmed Overwrite item's existing file, then the job's preset and, for a JPEG result, its quality and background, before reading anything, decodes the source upright, resizes it, lets go of the decoded source, encodes the result in the item's planned format, and saves it with `output.Write`, returning the failing step's own typed error.

`job.Run` runs a whole job off the GUI thread and returns every listed source's outcome. It first checks what applies to every item — the preset, and the JPEG quality and background when any result is JPEG — and `output.Prepare` then checks the output folder, format, collision policy, Overwrite confirmation, and that at least one source can be resized, all before the folder is created, then creates the folder, and plans every destination as the filesystem stands, so re-running a job plans around the earlier run's results rather than assuming them; any of these failing fails the whole job with its own typed error before anything is processed, and so does an output folder that can no longer be reached while the destinations are planned, which happens after the folder was created. Every listed source is then an item that starts Pending and ends Completed, Skipped, Failed, or Cancelled, passing through Processing while it is resized. A source the list could not use, such as an unsupported or corrupt file, ends Failed with the list's reason, and one listed without a reason or a checked format, as one whose check has not finished, with `ErrUnchecked`; either stays protected from being written over, and an item whose destination exists ends Skipped under Skip. The rest are processed in list order a few at a time — at most one fewer than the processors, so the GUI thread keeps one, and never more than four — and only while the memory the items in flight need stays within a 1 GiB budget by their estimates: the decoded source, as the content check's decoder reports it, the resized image, the filter's working memory for the source's dimensions, as `resize.WorkingBytes` bounds it, and 20 MiB for the decoder's and encoder's buffers; a source that needs more runs alone, so the job never decodes every source at once. Each source is decoded within its own estimate and resized only while the whole item still fits what was set aside for it, so one rewritten since its check to need more, to decode it or, as another format or shape, to resize it, is not resized beside the others but reported Pending again and processed alone, with the most any source needs set aside. Once the heap allocated 64 MiB or more while an item was processed, or while the items ended since the last collection were, together, its worker collects garbage before the item's memory goes to the next one, so what finished items drop does not pile up beside it, while an item that failed before decoding, such as one whose name was taken, adds next to nothing toward a collection. One item's failure, a panic included, is that item's error and never stops the others, but once an item fails to write, or is to be planned again, and the output folder can no longer be reached, the items still waiting end Failed with the folder's error rather than each after being decoded and resized, and the folder is not created again. Under Skip, of two sources with one name only the first is written; when it fails, the next is processed in its place, and the rest end Skipped once the name is written or another program wrote a file there after planning; under Rename and Overwrite, an item whose free name another program took after planning is planned again and saved under the first unused numbered name, keeping the reason its plan gave it, never replacing that file, since Overwrite replaces only the files that existed when the job was planned, while a confirmed replacement whose file changed since planning replaces nothing and fails with `ErrDestinationChanged`, which says where the file is if it was moved aside. An item's reason for not having its natural name is reported once it is Completed under a numbered name or Skipped, and in no other state. Cancelling stops new items from starting, stops the items in flight at their next cancellation check before their results take their names, so no partial file is left, keeps every completed result, ends the unfinished items Cancelled, an item that would have been planned again included, and returns once nothing is in flight. A temporary file a write could not remove is reported with its item whatever the item ends in. Each change of an item's state is reported, one event at a time on `Run`'s own goroutine, with the counts of every state, so the view can hand events to the GUI thread through the shell dispatcher and show the completed and total counts, the file being processed, and each item's status and error. The view runs this workflow end to end, as the next paragraph describes.

Start Resize checks first that no image is still being checked, at least one is Ready or is to be checked again, the selected preset is valid, and the JPEG quality and background fields — applied from their text even when focus never left them — and the output options are valid; each refusal, a field the options cannot apply included, is explained above the source list, and an invalid field beside it too. Under Overwrite, a confirmation whose safe answer is No asks before the job starts, and declining starts nothing. The job runs off the GUI thread, so the window can be moved, the list scrolled, and each image's state reviewed while it runs; the job section keeps room for its longest progress and never shrinks while the job runs, so the list below it stays in place. Start Resize is disabled, the source list cannot change — Add Images, Remove Selected, and Clear List are disabled and drops show the no-drop cursor, since its rows are the job's items, and a change that arrives all the same is refused with a notice the job's end clears — and the keyboard focus moves to Cancel Resize. Every row shows its image's state in words — Pending, Processing…, Completed, Skipped, Failed, or Cancelled — rewritten in place so the selection and scroll position survive, and the selected image's detail line says where its result was saved and why under a numbered name, which file a skip left untouched and why, why it failed, with the error's category (validation, unsupported format, read/decode, write/encode, or unexpected) and how to recover where that applies, or that it was cancelled before anything was saved. Above the list, the progress shows how many images are done of the total, by outcome, and the file being processed; Cancel Resize stops further images from starting, lets those in flight stop at their next safe point, and keeps every completed result; a cancelled job that has not stopped within five seconds — a read or write blocked on an unresponsive network drive cannot see the cancellation — is let go, its images still in flight shown Cancelled with why, so the list and Start Resize are available again. When the job ends, the summary counts the Completed, Skipped, Failed, and Cancelled images and any that left a file behind, a replaced file that could not then be deleted included, reading as cancelled only when an image was, and Open Output Folder is offered once the folder holds a result, a job that saves none leaving the previous job's folder offered; it opens the folder only when chosen, off the GUI thread, so a folder on a drive that stopped responding cannot freeze the window, and a folder that cannot be opened is reported in the status area at the bottom of the view, leaving the job's progress or summary in place. A job the planner refuses as a whole, such as one whose output folder cannot be created, is reported with its category and recovery, and the rows show their content checks again; a job that stops unexpectedly after it started keeps the results it reported and marks the other images Failed. Settings changed while a job runs apply to the next job, and every run plans afresh, so re-running a job saves numbered copies under Rename and skips the earlier results under Skip, and checks again each image whose content check failed, or that could not be found when it was added, so one that has since become readable, come back, or been replaced by a valid image is resized as it now is; the job section says so while it does, as no image starts until those checks finish, a job cancelled meanwhile ends the images it had not checked again Cancelled, and the list shows the checks made from the job's first update on, or once the job ends, a job let go included. Closing the window cancels a running job and waits up to ten seconds for its images in flight to stop, so their temporary files are removed.

Shared Win32 controls, dimension validation, confirmations, inline notifications, centralized strings, and accessibility conventions live in `internal/ui`. See [Shared UI and accessibility conventions](docs/ui.md) for keyboard, status, theme, and contrast guidance.

Display topology and physical-pixel coordinate services live in `internal/display`. The package enumerates connected displays with their device names, friendly monitor names where Windows provides them, native physical-pixel bounds, effective DPI, and primary status; assigns deterministic picker numbers (primary first); resolves the display under the cursor; computes virtual-desktop bounds with negative-coordinate support; converts explicitly between logical 96-DPI and physical-pixel measurements; and forwards display-topology (`WM_DISPLAYCHANGE`) and scaling (`WM_DPICHANGED`) notifications to subscribers through the shell window.

Raw screen capture lives in `internal/screenshot/capture`. The package captures one connected display at its current native pixel dimensions or an arbitrary virtual-desktop rectangle, including rectangles spanning monitors, and returns opaque physical-pixel RGBA images from off the GUI thread. The cursor is never part of the output, and app-owned surfaces are excluded by hiding them and flushing the desktop compositor before capture. Failures are typed so invalid geometry, a disconnected display, and native graphics failures are reported distinctly, and each kind is presented with its recovery path: a display that disconnected or a layout that changed mid-capture asks for a fresh display selection, and a native graphics failure names the failed operation and suggests switching a full-screen exclusive application or game to windowed mode. A failed capture never returns a blank image as success. Content the compositor excludes from capture, such as DRM-protected video or windows that opt out of capture, composites as black without an error, which the GDI capture path cannot distinguish from a genuinely black screen.

Screenshot output lives in `internal/screenshot/output`. The package delivers one captured image to both destinations — the Windows clipboard as a `CF_DIB` image and a PNG or JPEG file in the configured output folder — and reports the two outcomes independently, so a clipboard failure never discards a saved file and a save failure never discards a successful clipboard copy. The clipboard always receives the original captured pixels, never the output of JPEG encoding, marked so that Windows clipboard sync does not upload them to the user's other devices; they stay in the local clipboard history (Win+V). Files are named `Screenshot_yyyyMMdd_HHmmssfff` with a numeric suffix when the name already exists, are encoded into a temporary file in the destination folder, and are finalized only after encoding succeeds, so existing files are never overwritten and a failed write leaves no partial image, including on FAT32 and exFAT drives, which have no hard links.

Capture execution sessions live in `internal/screenshot/execute`. The Full Display pipeline hides the main window, captures the selected display through `internal/screenshot/capture`, restores it, and delivers the image through `internal/screenshot/output` — synchronously off the GUI thread, with the Screenshot view posting the completion through the shell dispatcher. The rectangle pipeline captures the region an overlay session selected while the main window was already hidden: it flushes the desktop compositor so the just-destroyed session windows cannot linger in the frame, reads the pixels, restores the window the session passed in, and delivers the same way. Windows are restored on every path, including hide and capture failures.

Rectangle selection sessions live in `internal/screenshot/overlay`. Starting Free Rectangle or Preset Rectangle capture hides the main window and floats a topmost toolbar with Capture and Cancel commands near the selection. Only one session can be active at a time. The session surface never activates, so it cannot rise above the toolbar, while the toolbar is activated to take keyboard focus: Escape and Cancel end the session without producing output, Tab and Enter work through the shell's message filter, and the Capture command stays disabled until a selection exists. Cancelling, session-creation failure, and application exit all destroy the session windows explicitly and restore the main window, and every input-capturing surface is visible while it intercepts input, so no invisible input-capturing surface can be left behind. If the display topology changes mid-session — a display disconnects, or the resolution or layout changes — the session is revalidated against the new virtual desktop: a selection that still fits keeps its exact dimensions and is moved back inside while the tint overlay or preset frame and the toolbar are resized and repositioned, and a selection that can no longer fit ends the session with an explanatory warning instead of leaving a stale overlay behind. The Capture command destroys the session windows first and the capture pipeline flushes the desktop compositor, then reads the rectangle's pixels off the GUI thread while the main window is still hidden, restores the window, and delivers the image through `internal/screenshot/output` — so no session visual can reach the output.

In a Free Rectangle session the whole virtual desktop is covered with a dimmed topmost overlay. The user drags on the dimmed surface to draw the selection — its interior stays visually clear, painted at the minimum alpha so it keeps capturing the pointer input that moves and resizes it, while the live width and height show in the toolbar — then drags the interior to move it, drags the eight handles to resize it, or types exact dimensions. Without a pointer, the session starts in the toolbar's width field: typing a width and height and pressing Enter creates a selection of exactly that size centered on the cursor display and moves the focus to Capture, where Enter captures it and the arrow keys nudge it by one physical pixel, or ten with Shift, as they nudge a preset frame. The toolbar follows the selection without covering it where practical and stays inside the virtual desktop on every display arrangement. The overlay renders through per-pixel alpha compositing: the desktop stays dimmed, the selection interior is painted at the minimum alpha so it stays visually clear, and the frame ring is painted outside the rectangle that will be captured, so even the handle squares astride the selection's edges cannot reach the output.

In a Preset Rectangle session the selected preset instead floats as an exact-size topmost frame above the desktop, centered on the cursor display. The frame's interior is fully transparent and click-through — clicks reach the applications beneath while the frame keeps its position and exact physical-pixel dimensions — and its opaque border ring is the drag handle that moves the frame, including across display boundaries, without ever resizing it; there are no resize handles. The toolbar shows the live width, height, and virtual-desktop X/Y coordinates; arrow keys nudge the frame by one physical pixel (Shift for ten), and typing exact dimensions resizes the active frame in place as an ad hoc edit that never modifies the saved preset. A preset larger than the entire virtual desktop is rejected with a validation message before the session opens, while a rectangle larger than one individual display is allowed whenever it fits the virtual desktop. The frame renders through the same per-pixel alpha compositing, with its border ring painted outside the rectangle that will be captured.

### Interactive demonstration

```bash
go run ./cmd/fnd01-spike
```

- `Ctrl+Alt+S` shows the topmost overlay. A registration conflict is reported without terminating the program.
- Drag the 8 px border to move the overlay. Its interior is transparent and click-through.
- Arrow keys move it by one physical pixel; `Shift+Arrow` moves by ten.
- `F9` hides the overlay, captures its rectangle, writes a `CF_DIB` clipboard image, and saves `fnd01-capture.png`.
- `Esc` closes the overlay and exits.

Optional flags set the initial physical-pixel geometry and output path:

```bash
go run ./cmd/fnd01-spike -x 100 -y 100 -width 1280 -height 720 -output capture.png
```

The compiled executable accepts the same flags directly.

## Native self-test

**Warning:** the self-test moves the mouse, sends real clicks, creates temporary topmost windows, and replaces the clipboard image. Do not interact with the desktop while it runs.

```bash
go run ./cmd/fnd01-spike -self-test
```

The self-test checks every connected display, signed hit-test coordinate decoding, exact physical overlay bounds and movement, a non-empty 1 × 1 overlay region, a real click through the interior into a separate Win32 window without moving the overlay, a real border drag, the specific hotkey conflict error, capture dimensions and known RGB content at every pixel, clipboard round-trip dimensions, and PNG decoding. It prints the temporary PNG path and leaves the captured image on the clipboard for interoperability checks.

To verify clipboard consumption through Windows Forms on PowerShell:

```powershell
Add-Type -AssemblyName System.Windows.Forms
$image = [System.Windows.Forms.Clipboard]::GetImage()
if ($null -eq $image) { throw 'No interoperable clipboard image' }

$image.Dispose()
```

Run PowerShell in an STA session (`powershell.exe -STA`) if the host is not already configured that way.
